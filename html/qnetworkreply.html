Detailed Description

A reply is a sequential QIODevice. Data becomes readable as it arrives, and finished() is emitted once at the end, on success or failure. An HTTP error status such as 404 sets error(), and its body stays readable.

See also QNetworkAccessManager and QNetworkRequest.

Differences from Qt

Only the attributes listed under QNetworkRequest::Attribute as reply attributes are produced; the others read back what the request stored. header() returns QByteArray. Unlike Qt, the whole response stays buffered until read, with no read buffer limit. There are no proxy errors, as proxies do not exist yet.

QVariant QNetworkReply::attribute(QNetworkRequest::Attribute code) const

Returns the attribute for code, or an invalid QVariant if it has none. Status, reason, redirect target and encryption are taken from the response; any other code returns what the request stored with QNetworkRequest::setAttribute(), which is how applications tag a request and find the tag again in the reply.

See also httpStatusCode() and request().

[virtual] void QNetworkReply::ignoreSslErrors(const QList<QSslError> &errors)

Continues despite the errors listed, and no others. Call this before the handshake or from a slot connected to sslErrors(). It does not carry over to a redirect that leaves the origin.

[slot, virtual] void QNetworkReply::ignoreSslErrors()

This is an overloaded function.

Continues despite every verification problem. Call this from a slot connected to sslErrors(). It removes the protection TLS gives against impersonation, and does not carry over to a redirect that leaves the origin.

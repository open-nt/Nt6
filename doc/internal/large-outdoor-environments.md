# Build 60 km twins from heightmaps, instances and state

Nt should build large outdoor environments the way whole-earth simulators do, not the way game engines do. Keep a double-precision geodetic truth on the CPU. Stream a 3D Tiles 1.1 quadtree in which each tile carries three layers kept apart: a heightmap terrain patch, instance lists of shared glTF assets with feature IDs, and a surface-material mask that drives procedural clutter, physics friction and sensor materials. Render everything relative to a camera-anchored local frame with reversed-Z depth. The research points to **heightmap patches rather than quantized-mesh** as ntmapgen's terrain content: heightmap terrain (CDLOD-style) can be edited at runtime, the same tiles can serve as Jolt collision, and every whole-earth product already pairs a heightfield renderer with a 3D Tiles client. Dynamics come from four mechanisms that scale to tens of millions of objects at almost no CPU cost: vertex-shader wind driven by an environment entity, GPU-generated clutter seeded from tile coordinates, a sparse per-object override table (intact, felled, destroyed, open) applied whenever a tile streams in, and an immutable terrain base with a vector-edit delta layer for craters and earthworks. Ray tracing and sensors (lidar, radar, GNSS line of sight, thermal) share the acceleration structures through instance masks over dedicated proxy geometry. Vegetation follows the Indiana Jones policy of building and compacting a BLAS once and then only refitting it, and opacity micromaps handle alpha-tested foliage. A CPU ray-cast path through Jolt keeps headless and CI runs deterministic. Almost the whole toolchain is available under MIT, BSD or Apache licences. The open risks are data licences rather than code: OSM share-alike, the non-commercial FABDEM, Google tiles that may not be cached, and imagery resolution. The research also suggests six concrete changes to the ntmapgen plan and the digital-twin survey, listed in the final section.

## Whole-earth simulators, not game engines, set the pattern for 60 km

The 60 × 60 km target sits beyond what game-engine terrain is built for. Epic's largest recommended Landscape is **8129 × 8129 vertices in 1024 components** ([UE Landscape Technical Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-technical-guide-in-unreal-engine)). That covers about 8 km at 1 m spacing or 16 km at 2 m. Enfusion allows **one TerrainEntity per world**, and a heightmap import on a 32.5 km terrain trips an allocation-limit assertion ([BI wiki: Terrain Creation Tool](https://community.bistudio.com/wiki/Arma_Reforger:World_Editor:_Terrain_Creation_Tool); [BI Feedback Tracker T181663](https://feedback.bistudio.com/T181663)). At ntmapgen's 1–2 m grid, a 60 km area is 30,000–60,000 posts per side, so it has to be a tiled pyramid, not a single heightmap.

The systems that handle this scale converge on a single recipe. Microsoft Flight Simulator uses a quadtree in which LoD equals the number of subdivision steps. It requests tiles from estimated screen size and measured bandwidth, draws a parent's data until the children arrive, hides cracks with skirts whose length scales with slope, and moved CPU node positions from float to double ([Asobo GDC deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). VBS Blue IG is a WGS-84 round-earth image generator over a whole-earth database, and VBS World Server streams the same terrain to VBS4, Blue IG and Cesium clients over OGC protocols ([BISim Blue IG](https://bisimulations.com/?p=651); [BISim release news](https://bisimulations.com/?p=2322)). The US Army's One World Terrain picked 3D Tiles because no single other format carried the data and metadata it needed. Its Well-Formed Format is an extension of 3D Tiles 1.1 and glTF ([MODSIM 2024 paper 11](https://modsimworld.org/papers/2024/MODSIM_2024_paper_11.pdf); [Cesium OWT](https://cesium.com/industries/mission-support/owt/)). The survey's choice of 3D Tiles 1.1 as the runtime container is therefore the defence-mainstream choice, not a civil-GIS compromise. OGC CDB 2.0 was approved in December 2023 and published in January 2026 ([OGC 23-034](https://docs.ogc.org/is/23-034/23-034.html)). Converters run from WFF to CDB, not the other way ([MODSIM 2024](https://modsimworld.org/papers/2024/MODSIM_2024_paper_11.pdf)), so CDB and OpenFlight stay import-only, as the survey already says. OpenUSD still has no ratified geospatial schema: AOUSD only formed groups and planned a geolocation proposal in 2025 ([Geo Week News](https://www.geoweeknews.com/news/alliance-for-openusd-announces-new-members-interest-groups-and-working-group-progress)).

### Heightmap patches beat quantized-mesh for dynamic terrain

Choosing the terrain technique settles the open question in the ntmapgen plan. CDLOD keeps the heightmap in a quadtree and draws each selected node with a single shared grid mesh displaced in the vertex shader. Each vertex morphs toward the coarser LOD, so no stitching is needed. The quadtree's only metadata is a min/max height per node: **about 3.5 MiB for a 32K × 32K heightmap**, which is the size of a 60 km world at 2 m ([Strugar, CDLOD paper](https://raw.githubusercontent.com/fstrugar/CDLOD/master/cdlod_paper_latest.pdf)). Strugar's datasets show the budget. A 488 × 304 km area at 10/5 m spacing with a 92 km view range used 90 MiB in total, and quadtree traversal cost under 0.1 ms per frame on 2010 hardware ([CDLOD paper](https://raw.githubusercontent.com/fstrugar/CDLOD/master/cdlod_paper_latest.pdf)). CDLOD is edit-friendly because only the edited texels and the min/max values of the affected nodes change. Precomputed triangulated (TIN) schemes such as chunked LOD and quantized-mesh have to re-mesh the affected tiles, and Strugar lists "no real-time terrain modification" as chunked LOD's main drawback ([CDLOD paper](https://raw.githubusercontent.com/fstrugar/CDLOD/master/cdlod_paper_latest.pdf)). Quantized-mesh is a gzipped TIN with uint16 u, v and height relative to the tile, plus an ECEF tile centre in double ([quantized-mesh spec](https://github.com/CesiumGS/quantized-mesh)). It remains Cesium World Terrain's format, but cesium-native keeps it alive for backward compatibility while implicit 3D Tiles becomes the newer path ([3d-tiles issue #489](https://github.com/CesiumGS/3d-tiles/issues/489)).

The recommendation is that **ntmapgen's canonical terrain is a 16-bit heightmap pyramid in the 3D Tiles implicit quadtree layout**. Each height tile is quantized relative to its own min/max, as quantized-mesh does, so a tile with 300 m of relief still gets millimetre steps. The `tileset.json` content of each tile is a regular-grid glTF mesh with skirts, so any 3D Tiles client (CesiumJS, 3d-tiles-tools, Cesium for Unreal) can display and validate the world. Nt itself renders terrain CDLOD-style from the height rasters. Quantized-mesh is then only an import format, for Cesium World Terrain or customer data. Implicit tiling fits naturally: tiles are addressed by `{level}/{x}/{y}`, each child's geometric error is half its parent's, availability lives in Morton-ordered subtree bitstreams, and bounding volumes must be boxes or regions, not spheres ([3D Tiles ImplicitTiling spec](https://github.com/CesiumGS/3d-tiles/blob/main/specification/ImplicitTiling/README.adoc)). Skirts remain necessary at boundaries between independently streamed LODs. Cesium always emits them for that reason ([Cesium community: skirts](https://community.cesium.com/t/skirts-tablecloth-overhangs/1864)), and in Nt's own renderer CDLOD morphing makes them unnecessary.

### A tile is a bundle of independently versioned layers

MSFS has a design detail worth copying directly. Each tile holds about 70 kinds of "marker" (DEM, aerial texture, water mask, vegetation mask and so on). Each marker is a state machine (REQUESTED, PROCESSING, AVAILABLE, FAILED) with versioned dependencies, and a dirty marker reloads and triggers its dependents. MSFS uses that mechanism for in-game terrain editing ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). For Nt, the layers of a tile are height, imagery, surface mask, instance list, LOS and collision proxies, and the twin override table. A crater edit then dirties the height layer, which dirties the CDLOD node bounds, the virtual-texture pages and the Jolt heightfield in one dependency pass. Battlefield 3 gives a resident-memory reference point: **32 MB of resident terrain** built from 133 × 133 16-bit height tiles and 66 × 66 masks in fixed pools ([DICE GDC12 deck](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)).

### Ground textures come from the surface mask, not the satellite image

The texel-density gap is a data problem as much as a rendering one. Sentinel-2 is 10 m imagery. Battlefield 3's procedural virtual texture reached only **32 samples/m against the 500–1000 samples/m needed up close** ([DICE GDC12 deck](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)). MSFS bridges the gap by choosing near, mid and far detail maps per pixel from a surface type, tinting grass from the aerial image, and synthesising aerials from altitude, slope and trees where imagery is bad ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). For Nt, the imagery is a far-field colour tint. Ground-vehicle views are carried by ntmapgen's per-texel surface mask, which feeds detail materials composited into a virtual texture of 256² pages with borders. The page table and atlas are done in software, BF3- and UE-RVT-style, rather than with Vulkan sparse residency, which keeps the path portable to Android and MoltenVK. Edits invalidate pages, which are recomposited the next frame, which is why BF3 found destruction decals cheap ([DICE GDC12 deck](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)). The surface mask should therefore be at least as fine as the 1–2 m height grid, and it is the most valuable layer ntmapgen produces.

## Doubles on the CPU, camera-anchored floats on the GPU, curvature in the vertices

The precision numbers are well established. Float32 at Earth radius gives about 0.5 m steps. Relative-to-centre (RTC) rendering, with the object centre minus the eye computed in double and folded into a float model-view matrix, is jitter-free for vertices **within about 131 km of the tile centre** ([AGI / Cozzi, "Precisions, Precisions"](https://help.agi.com/AGIComponents/html/BlogPrecisionsPrecisions.htm)). Per-tile RTC is therefore more than enough for 1–4 km tiles, and the GPU high/low split (RTE, about 1.35 cm worst case and +37.5 % vertex size) is needed only for very long primitives such as roads or power lines spanning many tiles. MSFS adds an "anchor space": a GPU frame whose origin is the camera and whose Y axis is the local surface normal, so the chain becomes local → anchor → view → projection ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). UE5 does the same with "translated world space" and recommends converting to it as early as possible ([UE5 LWC rendering docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/large-world-coordinates-rendering-in-unreal-engine-5)). For depth, reversed-Z with a float buffer took NVIDIA's test from 45 % indistinguishable depths to 0 % and makes an infinite far plane free. Vulkan's 0..1 depth range supports it natively ([NVIDIA: Depth Precision Visualized](https://developer.nvidia.com/content/depth-precision-visualized)). Logarithmic depth (Outerra: 1 cm at 10 km, about 10 cm at 100 km with a 24-bit buffer) is a reserve for orbit-to-ground views, because writing depth in the fragment shader disables early-Z ([Outerra: Logarithmic Z-buffer](https://outerra.blogspot.com/2009/08/logarithmic-z-buffer.html)).

Nt's concrete choice is ECEF doubles as the truth in Nt Twin, `D32_SFLOAT` reversed-Z with an infinite far plane, and an MSFS-style camera anchor rebuilt each frame on the CPU. Each tile, node or instance batch gets a float matrix from its double origin to the anchor. This is why the survey's demand for a double transform in Nt glTF (`transformD` or `QtGltf::DMatrix`) is a prerequisite and not a phase-6 refinement: ntmapgen phase 1 cannot be viewed correctly without it.

### Bake curvature into vertices, not only into tile placement

The ntmapgen plan bakes curvature "into the ECEF placement of each tile". That is correct in intent, but placement alone leaves each tile as a flat UTM patch on its own tangent plane, and neighbouring tiles then disagree at their shared edge by roughly the curvature drop across a tile. By d²/2R this is about 2 cm at 1 km from the tile centre and 8 cm at 2 km. This is an inference from geometry, not a sourced figure. The fix is cheap and follows quantized-mesh, which stores vertices relative to an ECEF tile centre ([quantized-mesh spec](https://github.com/CesiumGS/quantized-mesh)). For the glTF grid content, ntmapgen computes each vertex through PROJ, generation frame → ECEF, minus the tile centre, and stores the result in float32, so seams match exactly. For Nt's CDLOD renderer, which displaces a shared flat grid, the CPU computes in double, for each selected node, the mapping from that node's UTM grid coordinates to the camera anchor. That mapping is an affine part (which absorbs the UTM scale factor and the meridian convergence) plus a quadratic drop term. The vertex shader applies it to the float grid position. Over a node of a few kilometres the quadratic residual is sub-millimetre (again a geometric estimate), and the shader cost is a handful of multiply-adds.

The plan's `--flat` mode should be labelled non-geodetic. In flat mode GNSS output and line of sight beyond a few kilometres are wrong by up to the 280 m drop the survey computes, so Nt Sim should refuse to emit NMEA in that mode, or should flag it.

### Nt Twin must do its geodesy without PROJ

There is a dependency conflict between the two documents. The plan's §6 says the twin's WGS84 conversions and geoid conversion go "through PROJ", but the survey's decision is that Nt Twin depends only on Nt Core and builds for Zephyr. The research supports keeping that decision and narrowing the runtime problem. ntmapgen uses PROJ and GDAL offline, both MIT ([OSGeo/PROJ COPYING](https://github.com/OSGeo/PROJ/blob/master/COPYING); [GDAL LICENSE.TXT](https://github.com/OSGeo/gdal/blob/master/LICENSE.TXT)), and writes everything the runtime needs into `georef.json`: the ECEF tile transforms, the generation-frame definition, and a coarse per-tile geoid undulation grid sampled from EGM2008. Nt Twin then needs only closed-form WGS84 ↔ ECEF ↔ ENU, bilinear geoid lookup and, for MGRS and UTM strings, either a clean-room Krüger-series implementation or GeographicLib (MIT) behind an optional build flag ([GeographicLib](https://github.com/geographiclib/geographiclib)). Arbitrary CRS support stays in the offline tool.

## Separating identity from density keeps vegetation dynamic and affordable

The forest densities in the ntmapgen starter configuration show the scale involved. At 0.04–0.07 trees/m², every km² of forest holds 40,000–70,000 trees, so a 60 km area that is 40 % forest carries on the order of 60–100 million trees. This is computed from the plan's numbers, not sourced. MSFS generated **23 million trees with 6.3 million in the frustum**, placed with Halton sampling from per-tile vegetation masks and rendered as octahedral impostors with one draw per species per tile ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). Horizon Zero Dawn placed its world on the GPU at runtime from paintable density maps: **500+ asset types, 100,000+ objects, about 250 µs of GPU time and about 4 MB/km²**. Its stated goals were determinism and local stability ([Guerrilla GDC 2017 slides](https://www.guerrilla-games.com/media/News/Files/GDC2017_VanMuijden_GPUBasedProceduralPlacementInHorizonZeroDawn.pdf); figures from a search extraction of the slides, not a full read).

The two approaches answer different questions, and Nt needs both. **Anything with identity goes into ntmapgen's offline instance lists with feature IDs.** That covers trees, rocks, buildings, fences, poles and bridges: anything that can be felled, destroyed, collided with, hidden behind or bound to a twin property. These objects are deterministic, inspectable, editable and keyable into the entity store. **Anything without identity is generated on the GPU near the camera from the surface mask:** grass, low shrubs and ground clutter, following Ghost of Tsushima's per-blade procedural grass with noise clumping ([GDC Vault: Procedural Grass in Ghost of Tsushima](https://gdcvault.com/play/1027214/contactUs)). The seed for each cell hashes (tileX, tileY, layer, cell), so clutter never "swims" and every client sees the same field. This matches the survey's three-layer reading of Arma 3 and the plan's per-tile seeding. The research adds one refinement: the line between the two layers is "does it need a stable ID?", not "is it big?".

### The rendering pipeline: compute culling, indirect draws, impostors

The portable baseline is the 2015 Ubisoft/RedLynx GPU-driven pipeline, which gave Assassin's Creed Unity **about 10× more instances** than earlier titles through cluster culling, Hi-Z occlusion and indirect multi-draw ([SIGGRAPH 2015 GPU-Driven Rendering Pipelines](https://advances.realtimerendering.com/s2015/aaltonenhaar_siggraph2015_combined_final_footer_220dpi.pdf); [GamingBolt](https://gamingbolt.com/assassins-creed-syndicate-anvilnext-updates-dx12-integration-gpu-driven-and-more)). In Vulkan this is a compute pass over the instance bounds of the resident tiles (frustum, previous-frame Hi-Z and distance LOD) that writes `VkDrawIndexedIndirectCommand` arrays consumed by `vkCmdDrawIndexedIndirectCount`, which is core in Vulkan 1.2. Mesh shaders are an optional accelerated path, because Android and MoltenVK coverage was not verified. The LOD chain runs from the full mesh with wind, to a reduced mesh, to an octahedral impostor baked offline from the glTF, with dithered crossfade between levels so nothing needs alpha sorting. Octahedral impostors are the standard far LOD outside Nanite, with open ports for Godot, Houdini and three.js; the three.js port shows a 200k-tree browser forest ([Godot-Octahedral-Impostors](https://github.com/SIsilicon/Godot-Octahedral-Impostors); [three.js forum](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735)). The baker is an offline tool and should follow the `nt` prefix rule (`ntimpostor`), or be a stage inside ntmapgen's asset check. UE5's Nanite Foliage (assemblies, voxels, bone-skinned wind) shrank the Witcher 4 demo's largest tree from about 3.5 GB to 29 MB, but it is still Experimental in 5.7–5.9, and users report that voxelising ordinary meshes gives no speed-up ([Epic: Nanite Foliage](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-foliage); [UE forum](https://forums.unrealengine.com/t/new-nanite-voxel-foliage/2585978)). Its one lesson Nt can take now is that instancing parts *inside* a tree matters as much as instancing trees. That points to nested instance buffers in the culling pass later.

### Wind as twin state, shader as consumer

Wind should stay in the vertex shader, as the survey already proposes. Crytek's documented model has *main bending* of the whole plant and *detail bending* of leaves, driven by smoothed waves with weights painted per vertex, and it carried thousands of screen-filling plants in Crysis ([GPU Gems 3 ch. 16](https://developer.nvidia.com/gpugems/GPUGems3/gpugems3_ch16.html)). Assets carry those weights in `_WIND` or `COLOR_0`. glTF allows application attributes prefixed with an underscore, and `EXT_mesh_gpu_instancing` (ratified) carries per-instance TRS plus custom attributes such as `_ID`, a wind phase or a state value ([Khronos EXT_mesh_gpu_instancing](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Vendor/EXT_mesh_gpu_instancing/README.md)). The shader samples a low-resolution wind field texture. The field is produced from the environment entity's wind vector and gust parameters by a seeded, time-driven function, which keeps several viewers and the sensor simulation consistent, and it can be refined later with a Ghost of Tsushima-style simulated field ([GDC Vault: Blowing from the West](https://gdcvault.com/play/1027350/Blowing-from-the-West-Simulating)). A trample render target around each vehicle flattens grass and decays over time. UE's move to bone-skinned wind keeps culling bounds and shadow caching correct, at about 0.1 ms per 100k bones ([Epic: Nanite Foliage](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-foliage)). The cheap equivalent in Nt is to pad instance bounds by the maximum sway declared in the asset configuration.

### Stateful objects as a sparse override table applied on stream-in

Arma's state model is cheap and proven. A destroyed building swaps to a configured ruin model, or vanishes if there is none, and the original is hidden on every machine, which also removes its collision ([BI wiki: Building Configs](https://community.bistudio.com/wiki/Building_Configs); [BIS_fnc_createRuin](https://community.bistudio.com/wiki/BIS_fnc_createRuin)). Its bugs show where to be careful. `setDamage` on a dedicated server left both the original and the ruin visible remotely ([T159895](https://feedback.bistudio.com/T159895)), and in Reforger, streaming out an entity while its authority exists is "undefined behaviour" ([BI wiki: Reforger Multiplayer Scripting](https://community.bistudio.com/wiki/Arma_Reforger:Multiplayer_Scripting)). The Nt design follows from that. Every instance has a stable ID: an ntmapgen feature ID for placed objects, or a tile/layer/cell hash for procedural ones. Nt Twin holds a sparse table mapping each ID to a state enum, a transform delta, a timestamp and a source, and the historian records it. That table, not the tile, is authoritative: a tile streaming in applies its overrides before its first draw, so state cannot be lost on stream-out, and unchanged objects cost nothing. In the renderer, a state change moves the instance between variant batches during the culling pass. `EXT_mesh_gpu_instancing` has no per-instance materials, so appearance-only states use `KHR_materials_variants` or a state attribute read by the shader. Doors, hatches and valves are glTF nodes driven by twin properties, with keyframed motions through `KHR_animation_pointer` (ratified) ([Khronos KHR_animation_pointer](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_animation_pointer/README.md)). Replication sends compact operations ("tree 0x… felled at t, bearing 212°"), not geometry.

### Deformable terrain: an immutable base plus vector edits

Deformable terrain stays out of version 1, as the survey says, but the research settles its shape. MSFS never edits the source DEM. Its terraforming edits are vector shapes with heights and influence radii, rasterised on the GPU into distance fields and merged at load ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). BF3 drives craters from a destruction-depth map ([DICE GDC12](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)). MudRunner keeps mud on a second, finer grid with one dynamically updated channel ([Game Developer](https://gamedeveloper.com/programming/mud-and-water-of-spintires-mudrunner)). Nt should store terrain edits in Nt Twin as vector operations (crater at P with radius r and depth d; berm along a polyline; flood level in a polygon) in the historian. The operations are rasterised into a per-tile delta layer that dirties the height, virtual-texture and collision layers through the marker graph. Replay and networking then stay small and deterministic. Heightfields cannot represent undercut trenches or tunnels, so those need mesh inserts placed on the terrain.

## Physics runs on Jolt in double precision, with bodies only where something can touch them

Jolt (MIT) fits Nt's licence and the survey's choice. It shipped in Horizon Forbidden West and Death Stranding 2, supports wheeled, tracked and motorcycle vehicles through `VehicleConstraint`, has heightfield shapes, and runs on every Nt desktop and mobile target ([Jolt GitHub](https://github.com/jrouwe/JoltPhysics)). Its precision is documented. Float positions are accurate to about 5 km from the origin, while `JPH_DOUBLE_PRECISION` stays accurate "thousands of km" out **at a 5–10 % cost**, with queries returning floats relative to a base offset chosen by the caller ([Jolt docs](https://jrouwe.github.io/JoltPhysics/)). Determinism needs the same API call order and binary. `CROSS_PLATFORM_DETERMINISTIC` costs about 8 %, broadphase query results and listener callbacks arrive in non-deterministic order and must be sorted, and mixing float and double builds is unsupported ([Jolt docs](https://jrouwe.github.io/JoltPhysics/)). PhysX 5.6 is now fully BSD-3 including its GPU source, but GPU acceleration is CUDA-only ([NVIDIA blog](https://developer.nvidia.com/blog/open-source-simulation-expands-with-nvidia-physx-5-release); [CG Channel](https://www.cgchannel.com/2025/04/nvidia-open-sources-physxs-gpu-simulation-code)), which conflicts with Nt's cross-platform targets.

Nt Sim should build Jolt in double precision with cross-platform determinism on. It should simulate in a local ENU "physics region" of about 10 km around each cluster of active vehicles, with gravity along the region's up vector, and rebase the region as vehicles move. At 5 km from a region origin the gravity direction is off by under 0.05°, a geometric estimate. Jolt's own docs suggest splitting very large scenes into several `PhysicsSystem`s ([Jolt docs](https://jrouwe.github.io/JoltPhysics/)), which maps onto regions for widely separated vehicles. Terrain collision uses heightfield shapes built from the same 16-bit height tiles the renderer uses, with curvature applied relative to the region origin. The plan's separate `collision/` heightfield export should therefore become a view of the canonical height pyramid rather than a second copy, so that rendering and physics cannot disagree. Static trees and rocks get bodies only within a radius of a dynamic body, added in batches per tile into a static broadphase layer, because Jolt's collision cost scales with active bodies and batch insertion avoids a slow tree ([Jolt docs](https://jrouwe.github.io/JoltPhysics/)). Collision shapes come from the assets' collision proxies, not render meshes. Two gaps need benchmarks before anyone commits to them. No published numbers exist for millions of static Jolt bodies, and Jolt's tracked-vehicle fidelity has not been checked against defence-grade mobility models.

## Atmosphere, weather and water are environment state that feeds both pixels and sensors

The survey's "environment as twin state" holds up well: every technique below is driven by a handful of parameters. Those parameters are properties of an environment entity, so they can be bound to METAR or forecast feeds, replayed or scripted.

### Sky and time of day

Hillaire's 2020 LUT method is the practical default. It goes from ground to space with aerial perspective, its LUTs are small enough to regenerate every frame so haze and ozone can animate, and its reference implementation is **MIT** ([sebh/UnrealEngineSkyAtmosphere](https://github.com/sebh/UnrealEngineSkyAtmosphere); [EG Digital Library](https://diglib.eg.org/handle/10.1111/cgf14050)). Bruneton's 2017 rewrite (BSD) is the accuracy reference ([ebruneton/precomputed_atmospheric_scattering](https://github.com/ebruneton/precomputed_atmospheric_scattering)). The LUT sizes and timings, and the claim that the aerial-perspective froxel volume covers only the near range, come from the researcher's background knowledge and were not verified, because the paper PDF could not be fetched. Beyond the froxel volume, distant terrain should take transmittance from the LUT directly. Sun and moon positions should be a clean-room implementation of published Meeus-style formulas, not NREL's spa.c. SPA is accurate to ±0.0003°, but its C code is distributed under restrictive terms, is labelled closed source and requires a commercial licence from NREL ([NREL SAMPA](https://midcdmz.nrel.gov/sampa); [OSTI](https://www.osti.gov/doecode/biblio/29117); [pvlib](https://pvlib-python.readthedocs.io/en/v0.9.0/_modules/pvlib/solarposition.html)). The ephemeris code should share its time base (GPS time with leap seconds) with the plan's GNSS model, so that sun position, satellite geometry and recorded history agree.

### Shadows and global illumination

For a 60 km world under a moving sun, virtual shadow maps give the best raster quality, with 16k² virtual resolution in 128² pages rendered only where needed ([Epic: Virtual Shadow Maps](https://dev.epicgames.com/documentation/en-us/unreal-engine/virtual-shadow-maps-in-unreal-engine)). Their invalidation cost spikes under fast camera motion, which is the normal case for aircraft and vehicle views ([UE forum](https://forums.unrealengine.com/t/gpu-performance-hit-when-moving-camera-slow-virtual-shadow-maps/2367437)). MSFS combines cascades near the camera with ray-marching through a **300 × 300 km top-down heightmap** for terrain shadows ([Asobo deck](https://www.asobostudio.com/files/inline-images/Designing_Terrain_System_Fuentes_Lionel.pdf)). That second technique comes almost free in Nt, because CDLOD already holds the height pyramid. Where hardware ray tracing exists, ray-traced sun shadows scale with resolution rather than scene area. Diffuse GI that follows the time of day suits DDGI probe cascades around the camera: about 1 ms at 1080p on an RTX 2080 Ti in NVIDIA's implementation ([NVIDIA: RTX Global Illumination Part I](https://developer.nvidia.com/blog/rtx-global-illumination-part-i)). The RTXGI SDK's licence was not confirmed, so Nt should implement DDGI clean-room from the JCGT paper ([DDGI paper](https://cim.mcgill.ca/~derek/files/DDGI-lowres.pdf)).

### Clouds, rain, fog

The baseline for clouds is a Nubis-style ray march driven by a weather map with temporal reprojection, under 2 ms on PS4 for Horizon Zero Dawn ([Guerrilla: Nubis Evolved](https://www.guerrilla-games.com/read/nubis-evolved)). Nubis Cubed's voxel clouds (2023) support fly-through but need authored voxel data ([Guerrilla: Nubis Cubed](https://www.guerrilla-games.com/read/nubis-cubed)). A 2D weather texture (coverage, type, base and top heights) is the right interface for a twin. It can be filled from METAR cloud layers near airfields and from gridded forecasts (GFS, ECMWF open data) over wide areas; the licences and resolutions of those feeds were not verified in this research. Wetness, puddles and snow are material-parameter work. The twin-specific part is sensor physics. In fog, 905 nm and 1550 nm lidar differ by **less than 10 % in extinction** at equal power, provided the drop-size distribution is modelled ([Duthon et al., Applied Sciences 2019](https://mdpi.com/2076-3417/9/14/2843)). In 25 mm/h rain, 905 nm reaches about **twice the range of 1550 nm** ([adverse-weather survey, arXiv 2112.08936](https://arxiv.org/pdf/2112.08936)). Virtual lidars built from a Marshall–Palmer drop distribution and Mie scattering give extinction and backscatter coefficients ([Sensors 23(15):6891](https://mdpi.com/1424-8220/23/15/6891)). Many earlier rain and fog models were never checked against experiments ([arXiv 2003.06660](https://arxiv.org/pdf/2003.06660)), so Nt should treat its weather-sensor model as a tunable table per wavelength. Koschmieder's visibility-to-extinction relation and ITU-R P.838 rain attenuation are the usual first-order formulas for fog and radar rain, but this research did not verify either.

### Water

The ocean is a Tessendorf FFT with several cascades to hide tiling. Atlas's GDC 2019 talk covers spectrum-based sea states, buoyancy, wakes and explosions ([GPUOpen Atlas slides](https://gpuopen.com/gdc-presentations/2019/gdc-2019-agtd6-interactive-water-simulation-in-atlas.pdf)). Crest 4 on GitHub is listed as MIT, while Crest 5 is a paid closed product ([ecosyste.ms crest](https://awesome.ecosyste.ms/projects/github.com%2Fcrest-ocean%2Fcrest); [Unity Asset Store Crest 5](https://assetstore-fallback.unity.com/packages/tools/particles-effects/crest-water-5-oceans-rivers-lakes-268614)), so only the former is a usable reference. Sea state is a property of the environment entity mapped to spectrum parameters, and buoyancy for amphibious vehicles and ships needs a CPU-side displacement, either from readback or from a low-resolution CPU FFT. For the inland twins that dominate the use case, the plan's levelled water surfaces and carved watercourses are enough, with flow-mapped rivers. Shorelines and rivers were not researched.

## Sensors share one acceleration-structure scene through proxies and masks

The survey already says not to ray-trace render meshes for simulation. The research supplies the policies that make a dynamic world traceable.

### Acceleration-structure policy for a swaying, streaming world

NVIDIA's guidance is to rebuild the TLAS each frame rather than refit it, to refit BLASes only for limited deformation, and to keep all acceleration-structure work under **about 2 ms on async compute** ([NVIDIA RTX best practices](https://developer.nvidia.com/blog/best-practices-using-nvidia-rtx-ray-tracing); [updated](https://developer.nvidia.com/blog/best-practices-for-using-nvidia-rtx-ray-tracing-updated/)). Indiana Jones and the Great Circle settled the vegetation case. Dynamic foliage BLASes are built with fast-build, update and compaction flags, compacted, and then **only ever refit, never rebuilt**, because the foliage sways about a rest pose, so quality holds. Compaction cut BLAS memory from 1027 MB to 606 MB ([NVIDIA: Indiana Jones OMMs and compaction](https://developer.nvidia.com/blog/path-tracing-optimizations-in-indiana-jones-opacity-micromaps-and-compaction-of-dynamic-blass)). Opacity micromaps then cut the main trace pass **from 7.90 ms to 3.58 ms** by removing most any-hit alpha tests ([same](https://developer.nvidia.com/blog/path-tracing-optimizations-in-indiana-jones-opacity-micromaps-and-compaction-of-dynamic-blass)). OMMs are now `VK_KHR_opacity_micromap` as of Vulkan 1.4.351 ([digitalcitizen.life](https://www.digitalcitizen.life/vulkan-1-4-351-adds-new-ray-tracing-and-shader-extensions-for-developers/)) and run on Android hardware ([UL Benchmarks](https://benchmarks.ul.com/news/new-opacity-micromap-test-now-in-3dmark-for-android)). The bake belongs offline, with size caps: some Indiana Jones OMMs took hours and one reached 43 MB. NVIDIA's OMM SDK is open source ([NVIDIA-RTX/OMM](https://awesome.ecosyste.ms/projects/github.com%2FNVIDIA-RTX%2FOMM)).

The scale problem is the TLAS. Intel found that above **9 million instances** a monolithic TLAS update blew the frame budget and that partitioned updates were on average 7× faster ([Intel: Jungle Ruins](https://community.intel.com/t5/Blogs/Tech-Innovation/Client/Path-Tracing-Massive-Dynamic-Geometry-in-Jungle-Ruins/post/1691062); figure from a search snippet). A 60 km forest of tens of millions of trees cannot sit in one TLAS as individual instances. Nt should trace in three distance bands. Near the camera or sensor (hundreds of metres), individual tree and object instances, using per-variant static BLASes for hinged and damaged objects and refit-only BLASes for swaying near-field foliage. In the mid-field, a static, compacted proxy BLAS per tile that merges that tile's LOS and shadow proxies. Far away, terrain only, plus a canopy-height layer that ntmapgen can export from the instance list. Partitioned TLAS and cluster BLAS exist in Vulkan only as `VK_NV_*` extensions ([VK_NV_partitioned_acceleration_structure](https://docs.vulkan.org/features/latest/features/proposals/VK_NV_partitioned_acceleration_structure.html)). DirectX previewed cross-vendor CLAS and PTLAS on 2026-10-28, with PTLAS rebuilds at 0.79 ms against 2.88 ms ([Microsoft DirectX blog](https://devblogs.microsoft.com/directx/clas-ptlas-preview/)), which makes a Khronos multi-vendor equivalent likely but unconfirmed. Nt should treat partitions as an optional path behind a capability check, mapping one partition to one streamed tile, and keep the per-frame KHR TLAS rebuild as the baseline that lavapipe can test.

### Proxies, masks and two backends

Bohemia's engine keeps separate non-render LODs per model: Geometry for collision, Fire Geometry for ballistics (with armour as material thickness) and View Geometry for line of sight ([BI wiki: LOD](https://community.bistudio.com/wiki/LOD); [Arma 3 Damage Description](https://community.bistudio.com/wiki/Arma_3_Damage_Description)). The View Geometry semantics are from general knowledge, not a fetched page. ntmapgen's asset configuration already declares collision and LOS proxies. It should add a ballistic proxy and a sensor proxy, and the runtime should give each proxy set its own instance-mask bit, so one TLAS serves render rays, LOS rays, lidar rays and ballistics. Foliage can then be invisible to ballistics but solid to LOS and lidar. Inline ray queries in compute (`VK_KHR_ray_query`) need no shader binding table and no swapchain, which makes them headless-friendly. Indiana Jones uses rayQuery loops in production for its shadow rays ([NVIDIA Indiana Jones blog](https://developer.nvidia.com/blog/path-tracing-optimizations-in-indiana-jones-opacity-micromaps-and-compaction-of-dynamic-blass)). Nt Sim also needs a **CPU backend** that ray-casts the same proxies through Jolt, as CARLA's lidar does with physics raycasts ([CARLA sensors reference](https://carla.readthedocs.io/en/0.9.14/ref_sensors/)). It covers GNSS satellite visibility, LOS queries and low-rate lidar on machines without a GPU, and gives bit-exact replays. Nobody has documented whether GPU acceleration-structure builds and traversal are reproducible run to run, so certification-grade determinism should rely on the CPU path or on recorded sensor output.

### Lidar, radar, thermal and GNSS on that substrate

The lidar is a compute shader that traces one ray per beam and time slice. Instance transforms are interpolated to each ray's timestamp, which yields rolling-shutter and motion distortion without the motion BVH that Isaac Sim's RTX lidar requires ([Isaac Sim RTX Sensors](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/sensors/isaacsim_sensors_rtx.html)). Intensity comes from a material reflectance table, attenuation follows CARLA's model (default 0.004 m⁻¹, with probabilistic drop-off at low intensity) refined by the weather tables above ([CARLA FLidarDescription](https://carla.org/Doxygen/html/de/d6f/structFLidarDescription.html)), and the points stay on the GPU. Isaac Sim's reported real-time factors of 0.24–0.5 and its 0.4 Hz full-scan publishing show that the bottleneck is moving data out, not casting rays ([forum: RTF 0.24 on 5090](https://forums.developer.nvidia.com/t/low-rtf-0-24-in-isaac-sim-5-1-on-rtx-5090/356149); [forum: full scan](https://forums.developer.nvidia.com/t/slow-pointcloud2-publishing-with-publish-full-scan-on-ros2-rtx-lidar-helper/341849)). Radar is shooting-and-bouncing rays: a ray-query fan per chirp that records path length, the radial velocity of the hit instance from a per-instance velocity buffer, and a material reflection coefficient, accumulated into range-Doppler bins. SagittaSBR, Sionna RT and an OptiX SAR simulator are open references ([SagittaSBR](https://arxiv.org/html/2604.09243v1); [Sionna RT](https://arxiv.org/html/2504.21719v1); [OptiX SAR](https://ar5iv.labs.arxiv.org/html/2005.09736)), but no real-time performance figures were found. Thermal follows the defence split between a thermal solver and a radiance renderer. OKTAL-SE precomputes surface temperatures with diurnal heating and thermal shadows, then renders emission, reflection, sun and atmosphere with a GPU real-time path ([OKTAL-SE SE-FAST-IR](https://www.oktal-se.fr/download/14/electro-optic-infrared/4613/se-fast-ir-2.pdf); [SE-Workbench HWIL EO](https://www.oktal-se.fr/wp-content/uploads/2020/11/SE-Workbench_HWIL_EO.pdf)). VBS made a physics-based thermal sensor its default and ships sensors as plug-in DLLs ([BISim 23.2](https://bisimulations.com/?p=4021); [BISim](https://bisimulations.com/node/539)). For Nt, that means thermal properties per material class, a coarse 1-D diurnal heat solver stepped on the simulation clock, sun and sky inputs from the environment entity, engine heat from vehicle state, and a radiance pass. GNSS is the cheapest sensor: about 30 LOS rays per receiver per tick against the LOS mask. It completes the plan's §6 model (blocked satellites under forest and in urban canyons) at negligible cost.

All of this depends on one data change. **Materials need non-visual properties.** Isaac Sim assigns radar emissivity and reflectivity through non-visual material names ([Isaac Sim RTX Radar](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/sensors/isaacsim_sensors_rtx_radar.html)), and Blackshark's SYNTH3D terrain in VBS carries semantic material classes for sensors ([BISim / Blackshark](https://bisimulations.com/?p=5449)). ntmapgen's surface classes and asset materials should therefore carry a sensor-material ID that keys a table of IR emissivity, thermal conductivity, density and specific heat, lidar reflectance at 905 and 1550 nm, and radar permittivity. That table should be designed so that OWT's GGDM feature codes can map onto it.

### Headless and distributed simulation

The survey's fixed-step clock should run on logical time and advance as fast as possible when headless, with each sensor's tick rate an integer multiple of the step. Isaac Sim's pitfalls show why: points are discarded when a frame overruns, and the full rate is reached only when tickRate matches the scan rate ([Isaac Sim 6.0 RTX Sensors](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/sensors/isaacsim_sensors_rtx.html)). The same logical-time mapping is what FMI 3.0's Scheduled Execution and clocks need ([FMI 3.0](https://fmi-standard.org/docs/3.0)), and what HLA's time-advance request/grant (TAR/TAG) needs. HLA's federate interface was revised as IEEE 1516.1-2025 in August 2025 ([mystandards.biz](https://www.mystandards.biz/standard/ieee-1516-1-2025-21.8.2025.html); [NASA SIW 2025](https://ntrs.nasa.gov/api/citations/20250001356/downloads/2025_siw_TimeConstraints_010.pdf)). HLA, DIS and FMI can therefore be added later as gateways without changing the core. VBS4 runs headless and drives any CIGI-compliant image generator ([BISim Blue IG](https://bisimulations.com/?p=651)), which suggests a future product shape: Nt Sim as the host and an Nt viewer as the IG. Gazebo's experience shows that render-based sensors need a GPU even headless ([Gazebo headless rendering](https://gazebosim.org/api/sim/9/headless_rendering.html)). This is one more reason for the CPU sensor backend. There is also a dependency to fix. The survey ties sensor simulation to "the ray tracing layer on QRhi", but ray queries in compute need only Vulkan functions and a device, not a window or QRhi. GPU sensors should therefore live in an Nt Sim backend that uses Nt's generated Vulkan bindings without Nt GUI, so that Nt Sim stays headless.

Three findings change what ntmapgen must do. First, **Copernicus DEM is a surface model**, not bare earth: it includes canopy and buildings, so vehicles would drive over forest-height bumps. FABDEM's removal of trees and buildings cut forest mean absolute error from 5.15 m to 2.88 m ([Fathom paper](https://www.fathom.global/academic-papers/a-30-m-global-map-of-elevation-with-forests-and-buildings-removed/)), which shows how large the bias is, but its non-commercial licence rules it out as a default. The plan's terrain-conditioning stage should therefore add an explicit surface-to-terrain correction: lower the DEM under WorldCover tree cover and OSM forest, and flatten it under building footprints, before it flattens roads. This step is skipped wherever a LiDAR DTM exists. Second, the plan's default imagery source, s2maps.eu cloudless, has unverified licence terms for later years, and nothing in this research confirmed them. The defensible default is to build a mosaic from Sentinel-2 L2A under the Copernicus licence, or to use ESA's CC BY 4.0 composites, and to keep s2maps as an option once its terms are checked. Imagery at 10 m is far-field colour only, as the texturing section argues. Sub-metre orthophotos are a customer-supplied layer, because commercial and national imagery licences normally restrict redistribution in derived tiles. Third, ODbL should shape the tileset's structure, not just `ATTRIBUTION.md`. The OSMF's horizontal-layers guideline says that combining OSM with other data as separate layers does not create a Derivative Database ([OSMF Horizontal Map Layers](https://osmfoundation.org/wiki/Community_Guidelines/Horizontal_Map_Layers_-_Guideline)). ntmapgen should therefore write OSM-derived content (roads, OSM-sourced building footprints and instance tiles placed inside OSM polygons) as separate tilesets from the DEM, imagery and WorldCover layers, and record a source per feature in `EXT_structural_metadata`. The ODbL obligation then covers only those tilesets. Whether vegetation instances scattered inside an OSM forest polygon count as a Derivative Database is unsettled. The OSM wiki itself says vector tiles are a grey area that "would have to be decided by a court" ([OSM wiki: License/Use Cases](https://wiki.openstreetmap.org/wiki/License/Use_Cases)), so the conservative reading is to treat them as derivative. Defence customers who cannot accept share-alike on classified enhancements will supply national vector data, and the layered design is what makes that substitution possible.

Storage at the target scale is manageable. A 1 m DEM over 3,600 km² is 3.6 G posts, 7.2 GB as raw int16, plus about 33 % for the pyramid and a 2–4× lossless saving. At 2 m it is a quarter of that. Imagery at 0.5 m would be about 4–6 GB compressed. These figures are computed, not sourced.

The libraries are permissive where it matters: GDAL (MIT/X), PROJ (MIT), meshoptimizer (MIT), Draco, KTX-Software and Basis Universal (Apache-2.0), GeographicLib (MIT), libosmium (BSL-1.0), PDAL (BSD, for raw LiDAR point clouds), Jolt (MIT) and 3d-tiles-tools (Apache-2.0, for validating and packaging) ([3d-tiles-tools](https://github.com/CesiumGS/3d-tiles-tools); [GDAL](https://github.com/OSGeo/gdal/blob/master/LICENSE.TXT); [Jolt](https://github.com/jrouwe/JoltPhysics); [meshoptimizer](https://github.com/zeux/meshoptimizer); [libosmium](https://github.com/osmcode/libosmium); [PDAL](https://github.com/PDAL/PDAL/blob/master/LICENSE.txt)). Entwine (LGPL-2) should be avoided, and cesium-terrain-builder has been dormant since 2023 ([Entwine](https://github.com/connormanning/entwine/blob/master/LICENSE); [cesium-terrain-builder](https://github.com/geo-data/cesium-terrain-builder)). osgEarth's repository now carries an MIT licence dated 2026, but no tagged release under it was checked, and it is tied to OpenSceneGraph, so it is reference material only ([pelicanmapping/osgearth](https://github.com/pelicanmapping/osgearth/blob/master/LICENSE.txt)). Cesium Native (Apache-2.0) already implements tile selection, async loading, glTF decoding with Draco and meshopt, quantized-mesh and raster overlays ([cesium-native](https://github.com/CesiumGS/cesium-native)). Nt should still write its own 3D Tiles 1.1 selector on Nt glTF, for three reasons: Cesium Native pulls in a vcpkg tree (libcurl, spdlog, s2geometry and more) that conflicts with Nt's no-vendoring rule, the implicit-tiling and refinement rules are compact, and Nt's selector has to drive CDLOD heightmaps and twin layers that Cesium Native does not model. Cesium Native and 3d-tiles-tools then serve as test oracles in CI: the same tileset loaded by both must select comparable tiles, and every ntmapgen output must pass the validator.

## Recommended architecture and phased plan

The architecture uses the module boundaries already decided. Nt Twin (Nt Core only) holds ECEF-double entity poses, the environment entity, the sparse override table, terrain edit operations, the historian and native geodesy. Nt Sim holds the fixed-step logical clock, Jolt in double precision across physics regions, the CPU sensor backend, the GPU ray-query sensor backend built on Nt's Vulkan bindings without Nt GUI, the GNSS and NMEA model, and later the FMI, HLA and DIS gateways. The renderer (ntgltfview now, Nt Quick 3D later) owns the 3D Tiles selector and marker-graph streamer, CDLOD terrain, the virtual texture, GPU-driven instance culling, impostors, clutter, wind, the atmosphere, clouds and water, and the acceleration-structure manager. Nt glTF gains double node transforms, `EXT_mesh_gpu_instancing`, `EXT_meshopt_compression`, `EXT_mesh_features`, `EXT_structural_metadata`, pass-through of `_`-prefixed attributes, `KHR_animation_pointer` and `KHR_materials_variants`. ntmapgen produces everything offline.

| --- | --- | --- |

Terrain (ntmapgen phase 1) | Heightmap pyramid in implicit 3D Tiles with glTF grid-and-skirt content, curvature in the vertices, surface-to-terrain correction; CDLOD renderer with a per-node double mapping; Nt 3D Tiles selector | 3d-tiles-tools validates; seams below 1 mm; CesiumJS shows the same world |

This ordering differs from the survey in one respect. The survey places double-precision origins, 3D Tiles streaming and instancing in its last phase, but ntmapgen phase 1 cannot be viewed without them, so they belong at the start of the large-world track. The survey's headless twin core (its phase 1) can proceed in parallel, because it shares only the geodesy.

The changes the research suggests to the two documents are these. In **ntmapgen-plan.md**: answer open question 4 with heightmap patches and treat quantized-mesh as import-only (§3.10 and §9); bake curvature into vertex positions rather than only tile placement, and label `--flat` as non-geodetic (§2); add a surface-to-terrain correction step for the Copernicus surface model (§3.4); replace s2maps.eu as the default imagery with self-built Sentinel-2 L2A or ESA composites until its terms are verified (§1); split OSM-derived output into separate tilesets with per-feature source metadata (§3.11 and §7); merge `collision/` heightfields into the canonical height pyramid (§3.11); add ballistic and sensor proxies and a sensor-material ID to the asset and surface schema (§4); and move runtime geodesy from PROJ into a native implementation fed by `georef.json` (§6). In **digital-twin-survey.md**: move large-world precision and 3D Tiles ahead of sensors in the phase order (§4); decouple sensor simulation from QRhi and add a CPU sensor backend (§2.5); record the three-band ray-tracing policy and OMMs in §2.1b; and keep the deformable-terrain item, but specify vector edit operations as the twin state.

## Conclusion

The central result is that "dynamic" and "large" pull in the same direction once identity is separated from density. Everything that needs to change state, block a ray or carry a twin property gets a stable ID in an offline instance list. Everything else is regenerated deterministically from a surface mask that ntmapgen produces once. Terrain stays a heightmap because heightmaps are the only representation that is simultaneously streamable, editable, physics-ready and cheap to make curvature-correct per node. The engineering risk is therefore lower than the size of the world suggests: each technique recommended here has shipped at or beyond this scale (MSFS, Horizon, Indiana Jones, Battlefield 3), and each core library is permissive. What is genuinely unproven is narrower and should be tested early: Jolt with millions of static bodies, KHR TLAS rebuild cost at 10⁶–10⁷ instances before partitioned acceleration structures reach Khronos, and whether GPU sensor output can be made reproducible enough for defence certification.

The less obvious implication concerns data. Nt's competitive constraint is not rendering but what it may legally ship. A world built from Copernicus, WorldCover and Google Open Buildings can be distributed freely with attribution. One built from OSM carries share-alike obligations that defence customers often cannot accept. One built from Google tiles cannot be built at all. Designing ntmapgen's output as separable, source-tagged layers from the first phase is what lets a customer swap in national or classified data without regenerating everything, and that ability is worth more to the primary use case than any single rendering technique.
